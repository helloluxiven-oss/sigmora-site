How it works

A real org, not one long chat.

A loop around a single model is one improviser doing everything in prose. SIGMORA runs a bounded tree of specialised agents, each with its own instructions, its own model, and only the tools it was granted.

The org tree

An org is a tree of agent nodes: a lead orchestrator — the CEO — leading department heads (Marketing, Sales, Finance…), which lead workers.

Each node is a role, its own system instructions, a model, a tool allowlist, and its direct reports. Nothing is shared implicitly.

Delegation that bubbles up

Every manager node is given a delegate tool scoped to its direct reports only.

Calling it spawns a fresh, isolated agent run for that child — with the child's own role, instructions, model and tools — runs it to completion, and returns the result to the parent. Results bubble up the tree, and the lead synthesises the final answer.

How agents get tools and models

When a node runs it resolves its model — a per-tier default for lead, sub-agent or worker, or a per-node override — and is handed only the tools on its allowlist: file I/O, knowledge-vault search, deterministic compute, document and spreadsheet generation, plus extensible MCP servers and custom HTTP tools.

Any risky or irreversible tool is wrapped in a human approval gate.

Rails, audit trail, kill-switch

Hard caps on delegation depth, number of agent runs, total iterations, per-tool call budgets and wall-clock time — the clock is shared across the whole run, so one limit winds the entire tree down rather than leaving branches spinning.

A full audit trail of every start, delegation, tool call and result. And a privacy kill-switch — Internal mode — that forces every agent, lead and workers alike, onto a local model and blocks all cloud traffic.

The architectural bet

The model is a router. It never authors data.

LLMs hallucinate figures, which is a non-starter for anything touching finance or reporting. The fix here is architectural, not a bigger model.

Tools return structured objects
Not prose the next step has to re-read and re-interpret.
Code assembles anything with a number
Totals, metrics and tables are computed deterministically, so the figures in a report are exact and are never invented by the model.
The model writes the prose around them
It decides what to do and who to delegate to. It does not type the numbers you report on.
Which is why a small local model is still safe here
Trustworthiness for money and reporting comes from where the figures are computed, not from the size of the model doing the routing.
Connectors

Wired to the tools you already run.

Every connector is MCP-backed: you register the server, choose which of its tools it grants, and attach it to the agents that should hold it. Nothing is connected by default, and an agent only ever sees what you gave it.

This list is generated from the product's own connector catalogue rather than written by hand, so the site can't quietly claim an integration the app doesn't offer.

What we're not claiming

The limits, stated up front.

Marketing pages tend to go quiet exactly where a product is weakest. Here is where this one is today.

Semantic search
Knowledge-vault retrieval is keyword and frontmatter based. It is not embeddings-based semantic search yet.
Headless background service
Scheduled workflows fire while the app is resident in your system tray. It is not a fully headless service that runs without it.
Multi-tenant enterprise layer
It is single-user and local today. There is no shared or multi-tenant deployment.
Native first-party integrations
Connectors are MCP servers you register yourself. SIGMORA does not ship its own OAuth clients for Gmail, Slack or Sheets.
